# Offline baseline regression acceptance

Run `python3 scripts/check-baseline.py --research-python /absolute/venv/bin/python --log /absolute/new-audit.log` from the reviewed development checkout. Reuse the research environment with the versions in `research-ml/requirements.txt`; this runner does not install dependencies.

The runner records the revision, working-tree status and runtime versions, verifies the research dependency pins, runs its own rejection tests, then `scripts/check.sh core-base` and the five research suites listed in the research workflow. Core-base excludes the separately partitioned position-book and devnet-pool suites; their unchanged accepted baseline is not revalidated by this command.

Both the command exit code and its merged output matter. Any nonzero exit, `ResourceWarning:` or `Exception ignored` diagnostic stops acceptance, including a warning emitted during garbage collection after unittest reports OK. The final `BASELINE REGRESSION CLEAN` marker appears only after every stage finishes cleanly. Existing log files are never replaced. Review the recorded revision, working tree and full log before accepting Kali validation; this marker does not itself close B0 or authorize CI, merge, installation or execution.

The associated resource cleanup explicitly closes SQLite connections after transaction contexts in offline fixtures and quote-observer source helpers, and closes HTTP error responses in the read-only chain clients. Deadlines, admission policy, request limits and transaction behavior are unchanged. Quote-observer's source manifest hashes describe the revised development files; runtime identity remains 0.9.0. This is not a deployable observer release or an instruction to run its installer. Existing installed payloads and deployment inventory remain separate evidence; source cleanup is validated with offline fixtures only.

The follow-up cleanup closes the execution-cost reader's HTTP error response and the offline scanner backup exporter's database, plus the remaining scanner, quality-report and journal fixtures. The exporter regression verifies closure on both success and analysis failure, and preserves an existing report on the failure path. The deployment regression pins the revised exporter's source digest while retaining the original release manifest unchanged; a checkout of development source must not be presented as the installed release. No runtime install or scanner rebuild is part of this validation.
